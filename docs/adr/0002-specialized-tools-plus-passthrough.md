# 0002 - 全覆盖架构:专项工具精包装 + 通用执行器透传

日期:2026-10-16 | 状态:已采纳

## 背景

用户要求本包完全覆盖 cs CLI 的全部功能(约 20 个子命令)。工具面设计有两个极端:逐命令包工具,或不包装只让 agent 用 bash 直跑。cs 子命令性质差异极大:scan 需要凭证接线、后台执行、产物解析;而 findings/dedupe/export 等是即跑即得的前台命令。

## 决策

三层结构:

1. `codex_security_scan`:扫描专项精包装(后台 spawn、LLM 接线、并发上限、句柄落盘)。
2. `codex_security_status`:产物查询专项(状态机、findings 摘要、降级)。
3. `codex_security_run`:通用执行器,透传其余全部 cs 子命令(白名单排除 login/logout/mcp),前台执行、50KB 输出截断、超时控制、退出码透传。

安全约束放在 skill 纪律层而非工具拦截层:patch 类确认后执行,publish 类仅用户明确要求(用户拍板「透传+强纪律」)。

## 为什么不用 逐命令包工具(20+ 工具)

工具 schema 与文档面爆炸,每个命令的参数演化都要同步;且多数命令包装只增加一层无价值的转发。维护成本与收益不成比例。

## 为什么不用 纯 bash 直跑(不包装)

无法承载扫描场景的硬需求:凭证注入(密钥不能过 agent 上下文与命令行)、后台进程管理、产物解析、完成通知。scan 必须精包装。

## 为什么不用 工具层硬禁危险命令

用户明确选择透传;工具层拦截会使覆盖不全(用户要求完全覆盖),且 pi 自身权限模式已提供会话级闸门。纪律写进 skill,由 agent 行为约束。

## 后果

好处:能力面 = cs 全部命令(用户目标达成);工程量集中在 scan/status 两条需要接线的链路;cs 新增子命令时 run 天然兼容,无需改包。

代价:run 的参数是弱类型透传(TypeBox 只约束 command 与少量选项),agent 误用参数只能靠 cs 自身报错;危险命令的防线是文档纪律而非机制强制,依赖 agent 遵守 skill(以 pi 权限模式兜底)。
